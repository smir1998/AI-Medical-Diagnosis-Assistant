# MedLens·AI: evidence-based improvement roadmap

This note reviews the app as an **educational software project**. It is not a regulatory determination or a clinical validation plan. The current symptom dataset and simulated imaging output are not evidence that the app is safe or accurate for patient care.

## What the current app is doing

- `TrainingGrounds` trains a logistic model on the bundled 4,920-row Kaggle symptom-label file and reports a grouped profile holdout. `App.tsx` passes `onTrained={() => {}}`, so that model is not used by `SymptomChecker`.
- `SymptomChecker` still produces its own score from hand-authored disease weights. `ReportPanel` displays this score as confidence, which can be read as a calibrated probability even though no calibration is established.
- `ImageAnalysis` labels its result as a simulation; it does not inspect pixels or run a trained imaging model.
- The patient registrar accepts names, age, complaints, allergies and vitals. Before adding persistence, analytics or cloud services, define privacy, retention, deletion and export behavior.

## Recommended roadmap

| Priority | Improvement | Why it matters / implementation direction |
| --- | --- | --- |
| **P0 — keep educational scope clear** | Make “simulation” visible beside every output; replace “confidence” with “score” unless probability calibration is measured; mark red-flag content as educational guidance and direct urgent symptoms to local emergency services. | FDA CDS guidance evaluates intended use, inputs, algorithm, validation and how users are expected to rely on an output; a disclaimer alone does not determine regulatory status. If the product moves toward individual-patient diagnosis or image interpretation, seek jurisdiction-specific regulatory review before launch. [FDA CDS guidance and decision tool](https://www.fda.gov/medical-devices/digital-health-center-excellence/step-6-software-function-intended-provide-clinical-decision-support) |
| **P0 — make the product behavior coherent** | Either clearly separate the training sandbox from the symptom demo, or deliberately pass a trained model into a prediction workflow. If connected, display the model/version and data source and preserve a clear human review step. | Training results are currently not consumed by the symptom checker. A model trained in the browser does not improve the displayed symptom report until the inference path uses that trained model. Human-AI performance and clear user information are explicit FDA GMLP principles. [FDA GMLP principles](https://www.fda.gov/medical-devices/artificial-intelligence-enabled-medical-devices/good-machine-learning-practice-medical-device-development-guiding-principles) |
| **P1 — disclose data and evaluation limits** | Add a dataset card with source/version/license, row and class counts, label meaning, feature normalization, repeated-profile counts, known gaps and intended educational use. Show split method, support count and confidence intervals beside metrics; avoid accuracy-only claims. | The Kaggle rows are curated symptom/label examples, not a clinically representative patient cohort. Grouping identical symptom signatures reduces exact-duplicate leakage, but does not make this a clinical validation set. FDA guidance calls for representative data, independent test data and clinically relevant testing; TRIPOD+AI calls for transparent reporting of prediction-model development and evaluation. [FDA GMLP](https://www.fda.gov/media/153486/download?attachment=) · [TRIPOD+AI](https://www.bmj.com/content/385/bmj-2023-078378) |
| **P1 — improve the training experience** | Add epoch cancellation, load/error/retry states, class-balanced metrics, confusion matrix, macro and per-class recall, calibration plots, and a deterministic run record (seed, dataset version, parameters). Keep train/validation/test roles distinct; hold back an untouched test set for a final evaluation. | This improves reproducibility and makes weak classes and model uncertainty visible. The 41-row Kaggle `Testing.csv` should not be treated as robust independent clinical validation; assess independence and representativeness before using any test score as a performance claim. [FDA GMLP](https://www.fda.gov/media/153486/download?attachment=) |
| **P1 — protect registrar data** | Add a prominent demo-data notice, one-click clear/reset, safe CSV export, and a privacy statement. Do not add remote storage or telemetry of entered patient details without a defined consent, security and retention design. | WHO health-AI principles emphasize human autonomy, privacy, safety, transparency, accountability and inclusion. [WHO principles](https://www.who.int/news/item/16-05-2023-who-calls-for-safe-and-ethical-ai-for-health) |
| **P2 — accessibility and usability** | Add keyboard/focus support, semantic labels and live regions, non-color status cues, responsive tables, and reduced-motion handling. Test with screen readers and low-vision settings. | The current app is information-dense and uses animated/status styling. Accessibility makes educational workflows usable for more learners and should be validated with actual users.
| **Future research — genuine clinical models** | Treat real imaging or clinical decision support as a separate research/deployment program: obtain data rights, define one indication and intended population, involve clinicians and patients, validate on representative external data, assess subgroup performance and calibration, run human-factors studies, document hazards, and monitor versions/drift. | FDA's current AI device transparency guidance recommends communicating intended use, inputs/outputs, training/testing data, clinical performance, limitations, gaps and lifecycle monitoring. WHO recommends evidence of benefit and human oversight before routine health use. [FDA transparency principles](https://www.fda.gov/medical-devices/artificial-intelligence-enabled-medical-devices/transparency-machine-learning-enabled-medical-devices-guiding-principles) · [WHO AI-for-health guidance](https://www.who.int/publications/i/item/9789240029200) |

## Bottom line for product direction

The best near-term upgrade is **a truthful, polished teaching tool**: keep image inference explicitly simulated, separate the training model from the rule-based symptom demo until the model is intentionally connected, and publish its dataset and evaluation limitations in the UI. A clinical-use direction requires a defined use case, clinical evidence, representative data, safety engineering and regulatory review; model complexity alone is not the next step.

For AI-enabled medical devices, FDA's August 2025 PCCP guidance describes pre-specified changes and validation methods for controlled modifications. If this project ever becomes a regulated product, use a formal version/change-control process rather than silently retraining in the browser. [FDA PCCP guidance](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/marketing-submission-recommendations-predetermined-change-control-plan-artificial-intelligence)
